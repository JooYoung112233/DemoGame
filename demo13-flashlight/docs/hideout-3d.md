# 은신처 3D — 공간 규격 · 소품 정의서

> 3D 쿼터뷰 전환의 **첫 실제 공간**. 2026-09-08 그레이박스 → 2026-09-11 원화 기준 아트 개선.
> 실제 씬: `Assets/Scenes/Hideout.unity`. 과거 그레이박스 빌더는 `Assets/Editor/Hideout3DLayout.cs`.
> 아트 제작: `tools/build_hideout02.py` + `build_hideout_textures.py`; Unity 임포트/배치는 Editor API를 사용한다.
>
> 좌표 규약: 월드 = **XZ 평면**, 위 = **+Y**, **1u = 1m**. 2D판 좌표 `(x, y)`를 `(x, 0, y)`로 그대로 옮겨
> 시설 배치가 [2D판](safehouse.md)과 1:1로 대응한다. 관련: [3d-migration.md](3d-migration.md)

### 2026-09-11 — 수정 질감 인게임 적용

- 질문·확인: 수정한 쿼터뷰 하이드아웃 시안을 실제 게임에 적용할지?
- 사용자 결정: **“좋다 이느낌 인게임에 넣고 보자”** — 수정한 목재·금속·침구 표현을 실제 하이드아웃에 적용하고 게임 화면으로 확인한다.
- 구현 기준: MCP로 저장 씬과 런타임을 확인하고 기존 시설 기능·쿼터뷰를 유지한다. 인게임 조명 아래 가독성을 확인한다.
- 확인 결과: 저장된 Hideout02 연결을 그대로 사용해 Systems + Hideout 실제 Play Mode로 진입했다. 새 침구·표면 맵과 캐릭터·시설 바·이름표가 함께 출력되는 `ArtWork/HideoutReview/InGame.png`를 MCP `capture_game_view(source=screen)`으로 저장했다. 확인 시점 콘솔 오류 0건. 기존 인게임 조명은 검토 렌더보다 어둡고 차가운 편이다. 이후 플레이 상태가 바뀌어 작업대 버튼 검증은 완료하지 못했으며, 시설 패널 동작까지 통과한 것으로 간주하지 않는다.

### 2026-09-11 — 질감 수정과 셰이더 작업 순서 검토

- 사용자 질문(선택지): 지금 질감을 수정할지, 셰이더를 나중에 작업할지?
- 사용자 결정: **“수정해줘 그럼” — 대표 재질부터 수정하는 순서로 진행 승인**. 쿼터뷰와 검토 조명을 유지하고 바닥·철판·침구를 우선 수정한다.
- 제안: 현재 URP Lit에서 조명·색감·거칠기의 기본 기준을 고정하고, 바닥 목재·철판·침구 세 가지 대표 재질의 질감과 필요한 형태를 먼저 수정한다. 실제 게임 쿼터뷰 크기에서 비교·컨펌한 뒤 다른 소품으로 확장한다. 전용 스타일 셰이더는 그 다음에 검토한다.
- 근거: 현재의 반복 나뭇결·구름형 금속 얼룩은 표면 맵의 문제이고, 판처럼 보이는 침구는 형태도 원인이다. 후속 셰이더만으로 해결될 것으로 전제하지 않는다. 반대로 전체 소품의 텍스처를 먼저 완성하면 표현 방향 변경 시 재작업이 커진다.
- 반영: 목재 결 대비와 규칙성을 낮추고, 도장 철판의 넓은 얼룩·금속성·반사를 줄였다. 색 변화와 미세 표면 노멀을 분리했다. 매트리스 모서리와 베개를 둥글게 만들고 담요에 접힘·처짐·기운 자국을 넣었으며 매트리스 관통을 보정했다. 공유 맵을 사용하는 가구에도 같은 수정이 적용된다. 카메라·조명·URP Lit은 유지했다. 수정 결과는 사용자 컨펌 전이다.
- 작업 방식: 사용자 지시에 따라 Unity 임포트·검증·렌더를 MCP로 수행한다. 컴퓨터 화면 제어는 사용하지 않는다.

### 2026-09-11 — 1차 시안 질감 피드백·쿼터뷰 재확인

- 사용자 질문: “질감이 이상한데 어떻게 보이는가? 우리는 쿼터뷰로 가기로 했다.”
- 사용자 결정 재확인: **기존 3D 쿼터뷰 방향을 유지한다.** 원화의 배치와 분위기를 참고하되 정면에 가까운 구도로 바꾸지 않는다. 1차 질감은 승인된 상태가 아니다.
- 진단: 규칙적인 고대비 나뭇결, 금속에 넓게 퍼진 구름형 얼룩, 각진 침구와 평평한 담요가 원화의 절제된 손그림 표면과 어긋난다. 여러 재질에 비슷한 노이즈를 적용한 것이 원인이다.
- 교정: 게임 카메라 pitch 55°를 유지하고 방 회전을 이전 쿼터뷰 배치인 215°로 복구한다. 검토 렌더도 이 상대 각도에 맞추고 방 모서리가 잘리지 않도록 프레이밍한다. 재질 재작업은 큰 색면·낮은 대비·재질별 마모 위치를 기준으로 한다.

## 상호작용 — 디오라마 (2026-09-08 확정)

은신처는 **걸어다니지 않는다.** 2D판의 타르코프식 클릭 방식을 유지한다.
다만 2D판처럼 캐릭터를 **숨기지 않는다** — 클릭한 시설로 캐릭터가 가서 자세를 잡는 **디오라마**다.

| 시설 | 캐릭터 자세 | UI 자리 |
|---|---|---|
| (대기) 의자 | **앉아 있음** | — |
| 침대 | **눕는다** | **하단** — 화면을 가리지 않는 바 또는 시간 표기 |
| 요리대 | 앞에 선다 | **우측 패널** |
| 작업대·의료대·창고·라디오·파견·발전기 | 앞에 선다 | **우측 패널** |

### 원칙: UI가 캐릭터를 가리지 않는다
캐릭터가 시설에서 자세를 잡는 것이 이 화면의 요점이므로, 그 위에 패널을 덮으면 의미가 없다.

- UI는 **우측 도크**(840×960, 전 시설 동일)로 붙인다. 전체화면 패널 금지.
  시설마다 다른 자리에 띄우면 화면 크기가 들쭉날쭉해 산만하다 — **전 시설 동일**이다.
  (`Dock.Bottom`은 코드에 남아 있지만 쓰는 시설이 없다. 짧은 상태 표시가 필요해지면 그때 쓴다.)
- 도크 안: **좌상단 시설 이름 · 우상단 닫기 X · 나머지는 내용이 꽉 채운다.**
- 시설을 누르면 **카메라가 부드럽게 이동해** 방을 도크 반대쪽으로 밀고, 그 영역에 맞게 줌아웃한다.
  순간이동이 아니라 스무딩 이동이다.
- 화면 상단에 **시설 바로가기 바**가 있다. 소품 클릭과 완전히 같은 동작이다.

### 어디를 고치면 되는가 (파일 지도)

한 파일이 커지면 "이 화면 좀 고쳐줘"에서 고칠 자리를 찾는 데만 시간이 든다.
**기능 단위로 `partial`을 나눠 뒀다** — 아래 표에서 바로 찾아 열면 된다.

| 고치고 싶은 것 | 파일 |

수치는 **Control Panel(`Tools ▸ TopDown ▸ Control Panel`)의 "은신처 화면"** 항목에서
만진다 — 카메라 오소, 도크 폭·높이·여백, 축소 하한. 코드를 고치고 재컴파일할 필요가 없다.
(`GameTuning.asset`이 정본이고, 없으면 각 파일의 기본값으로 떨어진다.)

### 구현

| 구성 | 파일 | 역할 |
|---|---|---|
| **오케스트레이터** | `Scripts/TopDown/HideoutDiorama.cs` | 시설 클릭(3D 레이캐스트) → 캐릭터 이동·시설 응시·자세 → 카메라 포커스 → 기존 UI 열기. 씬에 있으면 `HideoutController`가 **캐릭터 숨김·카메라 고정·2D 클릭 판정을 양보**한다(`HideoutDiorama.Active`) |
| **역할 라벨** | `Scripts/TopDown/FacilityLabel.cs` | 소품 머리 위에 "침대·작업대·창고…"를 **상시 표시**. 걸어다니지 않는 화면이라 근접 E 프롬프트가 성립하지 않는다 — 무엇을 누를 수 있는지 한눈에 보여야 한다. `TextMesh`+`LegacyRuntime.ttf`, 카메라 향해 빌보드 |
| 시설 앵커 | `Scripts/TopDown/HideoutFacilityAnchor.cs` | 시설별 **캐릭터가 설 자리·자세(Stand/Sit/Lie)·UI 도킹(Right/Bottom/None)**. `moduleKey`는 `HideoutUI.Show(module)` 값과 일치해야 한다 |
| 카메라 연출 | `CameraFollow.SetFocus(focus, screenBias, orthoSize)` | 피사체를 화면 비율만큼 밀어 UI 자리를 비운다. `ClearFocus()`로 복귀. 도킹에서 편향 자동 산출(우측→캐릭터 왼쪽, 하단→캐릭터 위) |

### 현재 자세 범위

시설 9곳의 `moduleKey`, 상호작용 타입, 도킹 설정을 유지한다. 앉기·눕기 전용 모션은 이번 아트 패스의 범위가 아니며 현재 앵커의 서기(Stand) 설정을 보존한다. 기존 패널 도킹과 기능 버튼은 이미 구현되어 있다.

### 재생성 / 확인

1. `tools/build_hideout_textures.py` 실행(Python + NumPy/Pillow).
2. Blender 백그라운드에서 `tools/build_hideout02.py` 실행. `hideout02_blender_materials.py`로 Blender에도 같은 표면 맵 연결.
3. Unity MCP `eval_file`로 `tools/setup_hideout02.cs` 실행 → 임포트/프리팹 생성. `tools/unity_mcp_call.py`는 공식 `unity mcp --project-path` stdio 서버에 연결하는 클라이언트다.
4. 편집 모드에서 `tools/place_hideout02.cs` 실행 → 기존 시설 데이터를 복사하고 하이드아웃만 저장. 다시 실행해도 시설이 중복되지 않는다. 열린 하이드아웃에 저장하지 않은 변경이 있으면 중단한다.
5. `tools/render_hideout02.cs` → `ArtWork/HideoutReview/After.png`, `QuarterView.png`, `Detail.png`. **실제 Unity 모델의 검토용 조명 렌더**이며 플레이 중 UI 화면은 아니다.

침구만 갱신할 때는 Blender 백그라운드에서 `tools/refine_hideout02_surfaces.py`를 실행한다. `hideout02_bedding.py`는 전체 빌더와 공유하며 편집용 Blender 원본·침대 FBX·매니페스트를 함께 갱신한다. 이후 MCP로 `Cot01.fbx`를 임포트하고 검증/렌더한다. `MaterialBefore.png`와 `MaterialBeforeDetail.png`는 이번 질감 수정 전의 같은 카메라·조명 비교본이다.

검증 산출물은 같은 아트 폴더의 `ImportValidation.json`, `SceneValidation.json`, `SavedSceneValidation.json`에 남긴다. `tools/validate_hideout02.cs`로 시설 9종/키, 누락 스크립트 0, 포커스 참조, 반경 0.28m 캐릭터 공간(높이별 구 샘플)과 가구 충돌 0, 메시 UV·법선·탄젠트를 확인했다. 좁았던 파견·대기·조리 지점은 안쪽으로 이동했다. 이번 패스는 런타임 전투 코드·다른 맵을 수정하지 않는다.

### 남은 확인

- 원화의 손그림 윤곽·생활 흔적 밀도를 완전히 재현한 최종 아트는 아니다. 질감과 침구 형태를 수정한 시안으로 컨펌한다.
- 플레이 상태에서 시설별 UI·캐릭터 가독성은 별도 실제 플레이 검증이 필요하다. 이번 확인은 저장 씬과 에셋의 배선·공간·렌더 검사다.
- 외부 컨테이너와 실내 크기의 대응, 문 개폐 및 출입 연출은 후속 결정 사항이다.
