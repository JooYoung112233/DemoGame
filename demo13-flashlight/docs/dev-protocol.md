# 기능 추가 규칙 (BRB Feature Protocol)

> **이 프로젝트에 기능·콘텐츠를 추가할 때 반드시 통과하는 단일 게이트.**
> 문서 55+·스크립트 165+가 계속 늘어나는 상황에서 "방향이 어긋나지 않게" 하기 위한 규칙.
> 새 규율을 얹는 게 아니라, 이미 있는 규율(SSOT·즉시기록·GameTuning·런타임 규약)을 **한 기능 단위로 묶어 닫는다.**

---

## ⭐ 한 줄 규칙

> **"기능을 열었으면 같은 세션에 닫아라."**
> 한 기능 = **코드(5규약) + 값(GameTuning) + 기획(SSOT 문서 1곳) + 색인(MASTER)** 을 한 세트로 갱신하고 끝낸다. 반만 하고 넘어가면 그게 곧 드리프트다.

이 프로젝트가 실제로 두 번 겪은 드리프트(2026-06-30·06-16 문서 정합성 교정: **색인 누락 8종, 로어 중복 재서술, stale 서술**)는 전부 "기능은 넣었는데 세트를 안 닫아서" 생겼다. 이 규칙은 그 재발 방지다.

---

## 1️⃣ 착수 전 — 어디에 속하는지부터 정한다

새 기능/콘텐츠를 만지기 **전에**:

1. **SSOT 문서를 먼저 찾는다.** `docs/MASTER.md` 문서 맵에서 이 기능이 속한 시스템 md를 찾는다. 없으면 새로 만들고(§4), 애매하면 사용자에게 분류만 빠르게 확인한다.
2. **재서술 금지.** 세계관·로어는 **`gdd-core.md §5`가 유일한 출처**다. 다른 문서는 링크만 걸고 절대 다시 쓰지 않는다. 밸런스 수치도 마찬가지 — 값 자체를 여러 문서에 복붙하지 말고 `balance.md` 색인을 가리킨다.
3. **선행 결정 확인.** `dev-roadmap.md`의 "📋 기획 결정 대기"에 뿌리 결정(예: 게임 최종 목표)이 걸려 있으면, 그 위에 쌓는 기능인지 확인한다.

## 2️⃣ 구현 중 — 5대 런타임 규약 (컴파일은 되지만 런타임에 깨지는 지뢰)

코드를 쓸 때 아래는 **선택이 아니라 규약**이다. (출처: `CLAUDE.md` Key Patterns / `architecture.md`)

| # | 규약 | 요지 |
|---|------|------|
| R1 | **Editor State Preservation** | 런타임 스크립트는 `Start()`에서 값을 적용하지 않는다. 이벤트(`OnPhaseChanged` 등)로만 상태 변경. 에디터에서 세팅한 값 보존. |
| R2 | **Event-Driven Phase** | 낮/밤 반응 컴포넌트는 `Start`에서 구독만, `OnPhaseChanged`에서 반응, `OnDestroy`에서 해제. |
| R3 | **StatDB 중앙화** | 유닛/플레이어 스탯은 `StatDB.asset`에서 읽는다. 코드에 스탯 하드코딩 금지. |
| R4 | **UI = 프리팹 베이크 + Instantiate** | 새 UI 패널은 `EditorBake()` → `Resources/UI/*.prefab`. 뷰=`[SerializeField]`, onClick=`WireEvents()`, 동적 폰트=`ApplyFonts()`. 새 버튼 ref 추가 시 **재베이크 필수**. (상세 `ui-prefab-plan.md`) |
| R5 | **입력 = GameInput 셰임** | `UnityEngine.Input.*` 직접 호출 금지(New-only 모드라 런타임 예외). `GameInput.GetKeyDown/mousePosition/GetAxisRaw` 사용. 새 키는 셰임의 `KeyCode→Key` 맵에 추가. |

추가 배선 규약:
- **매니저/UI 신규 = Systems 씬에 배치** (additive 영속). 부트스트랩 자동생성은 폴백. (`architecture.md`)
- **밸런스 값 = GameTuning으로.** 튜닝 가능한 전역 스칼라는 `GameTuning`에 필드 추가 → Control Panel 자동 노출. 행 많은 표(아이템×지역, 유닛×스탯)는 데이터 파일/SO에 두되 **`balance.md`에 색인.** 코드에 매직넘버 금지. (`balance.md` §1)
- **세이브 = 스커밍 방지 계약 유지.** 레이드 진행은 인메모리 스냅샷, 디스크는 안전 맥락만. 새 저장 대상이 이 계약을 깨지 않는지 확인. (`save.md`)

## 3️⃣ 닫기 전 — DONE 게이트 (전부 ✅ 해야 커밋)

기능을 "끝냈다"고 하기 전에 아래를 모두 통과해야 한다:

- [ ] **코드** — §2의 R1~R5 및 배선 규약 위반 없음. (커밋 전 `unity-reviewer` 에이전트 권장)
- [ ] **기획 기록** — 이번에 내린 기획/밸런스/UX/시스템 결정을 **해당 시스템 md에 즉시** 기록(날짜/질문/결정/근거 + 하단 변경 로그). 세션 끝까지 미루지 않는다. (`design-keeper` 에이전트 활용 가능)
- [ ] **밸런스 색인** — 새 밸런스 값을 `balance.md` §1/§3에 등재(GameTuning 필드거나 데이터 파일 위치).
- [ ] **MASTER 동기화** — 새 문서를 만들었으면 `MASTER.md` 문서 맵에 등재. 시스템 상태가 바뀌었으면 상태 열 갱신. 죽은 링크 없음.
- [ ] **로드맵 반영** — `dev-roadmap.md`의 Phase/단계 상태·"미구현/마무리 필요" 목록을 갱신(완료분 ✅ 처리, 새 미완 항목 추가).
- [ ] **검증** — 컴파일 0 에러. 순수 로직=에디터 자가검증 메뉴 / 런타임=PlayMode 체크리스트 / 씬·콘텐츠=Play+스크린샷. (`playtest-verifier` 에이전트)
- [ ] **배포** — 브랜치에서 작업 → **PR로 main 병합**. main 직접 push 금지.

> 한 개라도 비면 그 기능은 "열린 채"다. 다음 세션의 나(또는 다른 PC)가 `dev-handoff.md`만 읽고 이어받을 수 있어야 닫힌 것이다.

---

## 4️⃣ 새 시스템(문서)을 만들 때

기존 시스템 md에 안 들어가는 **새 시스템**을 열 때만:

1. `docs/<system>.md` 생성 — 상단에 **역할 한 줄 + SSOT 선언**(이 문서가 무엇의 단일 출처인지). 로어는 §5 위임 링크.
2. 문서 구조: **현 상태 = 진실** 원칙. 결정이 바뀌면 본문을 덮어쓰고 하단 "변경 로그"에 이력.
3. `MASTER.md` 문서 맵의 알맞은 카테고리(🎯기획/🧱기술/⚔️전투/🎒인벤/💰경제/🏥의료/🏠안전가옥/🗺️월드/👥NPC/📖스토리/🎨렌더/🔧맵툴)에 한 행 추가.
4. 코드 핵심 파일이 생겼으면 해당 카테고리 하단 "핵심 코드" 줄에 추가.

## 5️⃣ 정리 주기 (organization) — 쌓이기 전에 턴다

기능이 계속 붙으면 문서/코드가 부패한다. 아래를 **주기적으로**(큰 기능 묶음 완료 시, 또는 월 1회) 돌린다:

- **문서 감사** — `doc-consistency` 에이전트로 MASTER 색인 vs 실제 파일, docs↔코드 수치/이름 불일치, 죽은 링크, stale 서술 점검·교정.
- **stale 서술 제거** — 마이그레이션·기획 변경으로 낡아진 서술은 그때그때 지운다(예: 아이소→탑다운 전환 시 구 셰이더 서술 삭제).
- **죽은 코드 정리** — 폐기된 스크립트/프리팹/빈 폴더 삭제. GUID로 씬·프리팹 부착 확인 후 제거.
- **문서 분할** — 한 md가 너무 커지면 분할(예: `Night_City_System_Draft` → gdd-core/progression/demo, items → items-crafting-farming). 분할 시 MASTER에 역할 명시.
- **핸드오프 갱신** — `dev-handoff.md`를 현재 위치(최신 작업·다음 후보·검증 대기)로 갱신.

## 요약 카드 (붙여두고 쓸 것)

```
기능 추가 = 열고 → 같은 세션에 닫기

BEFORE  SSOT 문서 찾기 · 로어/밸런스 재서술 금지
DURING  R1 에디터상태보존 · R2 이벤트페이즈 · R3 StatDB · R4 UI프리팹 · R5 GameInput
        + Systems씬 배치 · 값은 GameTuning · 세이브 계약 유지
DONE ☑  코드규약 ☑기획기록 ☑밸런스색인 ☑MASTER동기화 ☑로드맵 ☑검증 ☑브랜치→PR

정리   주기적으로 doc-consistency 감사 · stale/죽은코드 제거 · handoff 갱신
```

## 개발 ↔ QA 분업 (2026-07-11 확정)

**QA 에이전트** = 플레이·판정·문제 목록 (코드 수정 안 함) → **개발 에이전트(나)** = 원인 진단 → 시스템 확장/수정 → **다시 QA로 전달**. 이 왕복을 기본 루프로 삼는다.

- QA가 넘긴 문제는 **증상**이다. 코드에서 **원인을 확정한 뒤** 고친다(이 저장소는 "수치가 조용히 무효화되는" 함정이 잦다 — 씬에 박힌 stale 키, 미직렬화 필드, 고아 에셋, 도달 불가 코드).
- 밸런스 **판단**(더 열까/늘릴까)은 QA 몫, **노브 제공**은 개발 몫. 값을 임의로 정하지 말고 `GameTuning`에 노출하고 범위·반영 시점(런타임 즉시 / 빌더 재실행)을 알려준다.
- 개발이 QA에 넘길 때 **반드시 포함**: ① 이번에 바뀐 것 ② 재검증할 항목 ③ **씬 재빌드 필요 여부** ④ 조절 가능한 노브와 범위.
